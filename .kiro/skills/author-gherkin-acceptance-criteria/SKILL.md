# Author Gherkin acceptance criteria (shift-left)

This is a **pre-development** skill. It runs before a line of production code exists, with the Product Manager in the room. The output is reviewable acceptance criteria plus an explicit list of open questions — not a finished test suite, and not a guess dressed as a specification.

Wording rules are owned by #[[file:bdd-gherkin-standards.md]]. Coverage techniques are owned by #[[file:test-design-techniques.md]]. Domain vocabulary is in #[[file:domain-keyinfinity.md]]. Do not restate those files; apply them.

Two standing rules:

1. **Never invent a domain fact.** VAT rates, period calendars, HMRC paths, box numbers, role names, state names and thresholds come from the specification. If you do not have it, write `<confirm>` and add a question. Mark anything inferred as an assumption.
2. **Never write a credential.** Placeholders only: `YOUR_API_KEY_HERE`. No real tenant identifiers, VRNs, usernames or customer names.

## Step 1 — Restate the story in one sentence

Write the story as `As a <role>, I want <capability>, so that <business outcome>`. If you cannot fill all three slots from what you were given, that is the first finding. A story with no stated outcome cannot be tested, because there is nothing to assert.

Record: the role, the capability, the outcome, and which of the three were missing.

## Step 2 — Interrogate the story for missing rules

Work the checklist. Each row that cannot be answered from the story text becomes a question in Step 5, not an assumption in the Gherkin.

| # | Question | Looking for |
| --- | --- | --- |
| 1 | What exactly triggers this behaviour? | The single `When` |
| 2 | What must already be true? | `Given` preconditions, and which are `Background` material |
| 3 | What is the observable outcome? | A `Then` someone can see, not an internal state change |
| 4 | What are the inputs, and what are their valid ranges? | Partitions and boundaries (Step 3) |
| 5 | What should happen when input is invalid, empty, or at a limit? | Negative criteria — usually absent from the story |
| 6 | Who is allowed to do this, and who is not? | Role/permission criteria |
| 7 | Does behaviour depend on prior state? | A state machine (Step 3) |
| 8 | What happens on a second attempt, or a concurrent one? | Idempotency, double-submission |
| 9 | Which tenant's data is in scope? | Tenancy isolation — mandatory for multi-tenant SaaS |
| 10 | What third party is involved, and what if it is slow, down or rejects? | Stubbing need, timeout and failure criteria |
| 11 | Does any value depend on a date, period or deadline? | Time-dependent boundaries |
| 12 | What must be audited, logged or notified? | Side-effect criteria |
| 13 | Is this generated by the model-driven platform? | Regeneration risk, locator strategy |
| 14 | What is explicitly out of scope for this story? | Prevents scope creep in the AC |

Rules:

1. Ask about the negative and the unhappy path first. Stories are written optimistically; the gaps are almost always there.
2. One missing rule, one question. Do not bundle five uncertainties into "needs clarification".
3. If the story describes a UI mechanic ("tick the box, then the green banner shows"), translate it back into the business rule before writing anything, and confirm the translation with the PM.

## Step 3 — Identify equivalence classes and boundaries

For each input the story exposes, list the classes that behave alike and the limits between them. This is the shift-left half of #[[file:test-design-techniques.md]] — enough to prove the criteria are complete, not the full `Examples` table. If the rule needs a full table, that is the `design-test-cases` skill.

Produce one table per input:

| Input | Valid classes | Invalid classes | Limits | Known? |
| --- | --- | --- | --- | --- |
| submission amount | positive, zero | negative, non-numeric, over maximum | 0.00, maximum | maximum `<confirm>` |
| transaction date | within period | before period, after period | period start, period end | calendar `<confirm>` |

Rules:

1. Behaviour depends on prior state? Add a from-state / event / to-state table and ask which transitions are legal. Missing transitions are the most common AC gap.
2. A limit nobody can name is a question, not a number. Write `<confirm>` and move on.
3. One criterion per class and per limit. If two classes share an outcome and a reason, they are one class — merge them and say why.

## Step 4 — Write the acceptance criteria as Gherkin

Declarative, business language, third person, one behaviour per scenario. No selectors, URLs, verbs, status codes or payloads. Tags follow the taxonomy in #[[file:bdd-gherkin-standards.md]]: one layer tag, at least one suite tag, at least one feature-area tag.

Draft the happy path first, then one scenario per invalid class, then the permission and tenancy cases.

```gherkin
@api @smoke @vat
Feature: VAT return finalisation
  # Coverage note: happy path, invalid-state rejection, role restriction.
  # Open questions tracked in KEYINF-0000 - do not implement until closed.

  Background:
    Given the accountant is working in their own tenant
    And a VAT return exists for the current period

  Scenario: Accountant finalises a complete draft VAT return
    Given the draft VAT return has no outstanding validation errors
    When the accountant finalises the return
    Then the return is recorded as finalised
    And the return can no longer be edited

  Scenario: A return with outstanding validation errors cannot be finalised
    Given the draft VAT return has at least one outstanding validation error
    When the accountant attempts to finalise the return
    Then finalisation is refused
    And the return remains a draft

  @permissions
  Scenario: A read-only user cannot finalise a VAT return
    Given the user has the read only role
    When the user attempts to finalise the return
    Then finalisation is refused
```

Rules:

1. Where the outcome is genuinely unknown, write the scenario with `<confirm>` in the `Then` and list it in Step 5. A scenario with an invented expected result is worse than no scenario — it will be implemented as written.
2. Keep placeholder names as business terms in `<lowerCamelCase>`, never field IDs.
3. Add a one-line coverage note in the feature header stating what this set covers. It makes the gap visible at review.
4. Mark the feature file as not-yet-implementable while questions are open. Tag with `@ignore` plus the ticket link if it is committed before the answers arrive.

## Step 5 — Surface the unanswered questions for the Product Manager

Output a single table. This is the artefact that goes to refinement, and it is often the most valuable part of the work.

| # | Question | Why it blocks | Blocking? | Assumed if unanswered |
| --- | --- | --- | --- | --- |
| 1 | What is the maximum submission amount? | Cannot write the upper boundary criteria | yes | none — left as `<confirm>` |
| 2 | Can a rejected return be amended, or must it be superseded? | Changes the state machine and the editable flag | yes | none |
| 3 | Is a finalised return visible to the approver before submission? | Decides whether a permission scenario exists | no | assume yes, flagged |

Rules:

1. Blocking questions mean the story is not ready. Say that plainly rather than filling the gap with a plausible number.
2. Where you must proceed, state the assumption in the table **and** as a comment in the feature file, so it is visible at both ends.
3. Phrase questions in the PM's language, about behaviour and business consequence, not about test mechanics.

## Step 6 — Flag untestable wording

Scan every criterion for wording that cannot fail. Each one needs a measurable replacement, and the replacement must come from the PM, not from you.

| Untestable wording | Problem | Ask for |
| --- | --- | --- |
| "fast", "responsive", "quickly" | no threshold | a number and the percentile |
| "user-friendly", "intuitive" | not observable | a specific interaction that must succeed |
| "handles errors gracefully" | no stated outcome | the message, the state and the recovery path |
| "works as expected" | no oracle | the expected value, and who owns it |
| "secure" | unbounded | the specific control: authentication, authorisation, encryption |
| "should generally" / "where appropriate" | no rule | the condition that decides |
| "all relevant data" | undefined set | the exact fields |
| "supports large volumes" | no scale | the volume, and the acceptable duration |
| "matches KEYPrime" | oracle is a legacy product | confirm whether parity is in scope and who owns the reference — see #[[file:domain-keyinfinity.md]] |

Rule: never silently repair untestable wording. Quote the original, propose a testable rewrite, and get it confirmed. Rewriting it yourself turns a product decision into a test author's guess.

## Step 7 — Review gate before handing back

Hand back only when every box is ticked:

1. One behaviour per scenario, one `When`, one assertion concern.
2. At least one negative criterion exists.
3. Permission and tenancy criteria exist, or are explicitly out of scope and recorded as such.
4. No invented domain facts; every unknown is `<confirm>` with a matching question.
5. No secrets, no real tenant identifiers, no customer names; placeholders are `YOUR_API_KEY_HERE`.
6. No UI mechanics, no HTTP detail, no SQL in the Gherkin.
7. Open questions table is attached, with blocking status.
8. Coverage note states what is covered and what is not.

## Deliverable shape

Return four things, in this order:

1. The restated story, with any missing slot named.
2. The acceptance criteria as Gherkin.
3. The open questions table for the PM.
4. The untestable-wording findings, with proposed rewrites.

Then stop. Deriving the full `Examples` tables is the `design-test-cases` skill; writing bindings is #[[file:step-definitions.md]].
