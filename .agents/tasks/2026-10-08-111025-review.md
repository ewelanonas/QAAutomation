# C# BDD Selenium automation template — full review

The template is complete and working: six projects, 18 passing scenarios across API, UI and E2E, `Build succeeded` with 0 warnings, and a README that genuinely gets a non-C# QA from nothing to a green run. The three hard rules in `context.json` are all honoured, and honoured structurally rather than by convention — no live content count is asserted anywhere, nothing touches the carousel or the animated counters, and `ContactUsPage` has no submit method with the reason written out at the top of both the page object and the feature file. What is left is drift between the binding steering in `.kiro` and what was actually built, plus one real security gap in failure-artefact capture.

Watch for: failure artefacts write page source and browser console logs unmasked, which `ui-automation-selenium.md` §6.5 explicitly forbids (confirmed); `step-definitions.md` still places the DI factory, scenario contexts and hooks in `Core/Support` while the template puts all three at test project roots, and unlike `tech-stack.md` and `bdd-gherkin-standards.md` that steering file was never amended to record the deviation (confirmed); the two `Examples` tables in `PageListing.feature` carry no expected-outcome column, which `bdd-gherkin-standards.md` requires (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Layering and suite separation are enforced by the project files rather than by convention: `Core` carries no `ProjectReference` at all, `UI` and `Api` reference only `Core`, `Tests.E2E` is the single project referencing both layers, no test project references another, and `Tests.Api` registers no driver and has no hooks class so it cannot start a browser. All 16 packages are pinned centrally with no `Version` attribute in any `.csproj`; none of the three banned Selenium packages and no `FluentAssertions`.

`ElementWaits` is the only file containing a `WebDriverWait` or an `Until` lambda, implicit wait is pinned at zero, and scans find no `Thread.Sleep`, no polling loop, no `.Result`/`.Wait()`/`GetAwaiter`, no `async void`, no `var` and no LINQ operator outside an explanatory comment. The mechanical guard behind the LINQ ban, however, is Windows-only and would silently stop enforcing on a Linux agent.

The live-content rule is implemented with its reasoning attached. `PageListingSteps` asserts `X-WP-Total` is present and parses to a positive integer rather than asserting today's value; the one `Should().Be(1)` in the API suite is slug uniqueness, not a content count, and says so; the E2E assertion uses `ContainEquivalentOf` with a comment on why equality is not assertable, which closes off the obvious future "tightening".

Two behaviours of the live site that the plan did not anticipate are handled and written down: the contact form's fields sit at zero opacity until scrolled into view (solved by navigating to the page's own `#form` anchor, so no click races anything) and a ten-second newsletter modal covers the viewport (solved by a look-then-close component, because an unconditional wait would burn the full timeout on every click). Neither is guessable from the code alone, and both are explained in the README.

Credentials are placeholders throughout, nothing logs an `Authorization` header or a cookie, and configuration validation rejects any non-HTTPS base URL. The exception is `FailureArtefacts`, which writes the full DOM and the browser console log to disk unmasked. On the current marketing-site target there is nothing to leak; the template's stated migration path points it at authenticated multi-tenant SaaS, and the warning comment sits where the masking should be.

### Failure artefacts are written unmasked

`src/QAAutomation.Core/Support/FailureArtefacts.cs` captures four files per failed scenario. `SavePageSource` writes `driver.PageSource` straight to disk, and `SaveConsoleLog` appends every `LogEntry.Message` as-is. The class header carries an accurate warning:

> SECURITY: page source and console logs are raw application output. They can contain tokens, session identifiers, email addresses and other personal data.

`ui-automation-selenium.md` §6.5 does not stop at a warning — it says "Mask before writing, mask by allow-list, and never attach an unmasked capture to a widely readable artefact store." The warning documents the risk; it does not reduce it.

On the current target this is inert. The marketing site has no login, no session, no PII in the DOM. The problem is what the template teaches: the stated migration path in README §10 is to repoint `Site:BaseUrl` and `Api:BaseUrl` at KEYinfinity, which is authenticated multi-tenant SaaS. At that moment every failed UI scenario starts writing a full authenticated DOM and a console log to `test-results/`, and §6.6 says those artefacts are what CI publishes on failure. The masking hook belongs here, before that happens — a small allow-list pass over the console text and a redaction of known token-shaped attributes in the page source, or, if that is judged premature, a deferral recorded in `ui-automation-selenium.md` so the gap is a decision rather than an omission.

### Steering and implementation disagree about where wiring lives

`step-definitions.md` is specific on three points:

- "Registration lives in one `[ScenarioDependencies]` factory method in `src/QAAutomation.Core/Support`"
- "Contexts live in `src/QAAutomation.Core/Support` and are registered scoped"
- "Hooks live in `*Hooks.cs` under `Support`, never in a step class"

The template places all three at each test project root: `ApiScenarioDependencies.cs`, `UiScenarioDependencies.cs`, `E2EScenarioDependencies.cs`, `PageApiContext.cs`, `SiteNavigationContext.cs`, `EnquiryFormContext.cs`, `CrossLayerContext.cs` and two copies of `WebDriverHooks.cs`.

The reasons are sound and they are written down in the files themselves: Reqnroll only discovers `[ScenarioDependencies]` and `[Binding]` inside a test assembly, a shared `[Binding]` hook would launch a browser for the API suite and destroy suite separation, and a context holding Refit contract records in `Core` would invert the one-way dependency direction. Nothing here should change in the code.

What makes it a finding is the asymmetry. Plan item 1 required steering to be updated first "so the rest of the build is compliant rather than retro-justified", and that was done for `tech-stack.md` (three package rows plus the `AddRefitGeneratedClient` note) and `bdd-gherkin-standards.md` (the `@marketing` row). `step-definitions.md` was left alone, so the binding steering now describes a layout the repository does not have. The next person to read that file and move a context class into `Core` will break the build and be technically compliant while doing it. The fix is three amended sentences in the steering file, not a line of C#.

The same drift accounts for the missing `src/QAAutomation.Core/TestData/` folder in `project-structure.md`'s tree. No builder exists yet and `Bogus` is reserved, so an empty folder would be noise — but the steering tree and the repository should agree one way or the other.

### `Examples` tables without an expected-outcome column

`bdd-gherkin-standards.md` lists six rules for `Scenario Outline`. Rule 4 is "Add an expected-outcome column. A table of inputs with no expected result is not a specification."

`tests/QAAutomation.Tests.Api/Features/PageListing.feature` has two tables, each with a single `pageSize` column:

```gherkin
    Examples: accepted page size boundaries (boundary value analysis)
      | pageSize |
      | 1        |
      | 100      |
```

The feature file explains the choice — the accepted and rejected partitions are split into two outlines because their `Then` differs, so an outcome column would be constant for every row. That is a reasonable reading, and plan.md records it as decision D13. But plan.md is a task artefact, not steering, and the rule it waives is unqualified. Either add the column (`| pageSize | outcome |`) or add the split-table exception to `bdd-gherkin-standards.md` so the next author inherits the decision rather than re-deriving it.

`EnquiryForm.feature` gets this right for comparison: its `mandatory` column is the expected outcome, and the comment above the table says so.

### The LINQ guard does not run everywhere

`Directory.Build.targets` is the mechanical half of the no-LINQ rule, and it works — verified during the build, and verified again here at 0 warnings with no offending file present. Two properties limit it:

```xml
  <Target Name="WarnOnLinqUsage"
          AfterTargets="Build"
          Condition="'$(OS)' == 'Windows_NT'">
```

and the `Exec` runs `findstr`. On a Linux or macOS build agent the condition is false, the target never runs, and the rule stops being enforced with no signal that it has. CI is parked, so nothing is broken today. The cost of recording it is one comment line in the target and one sentence in README §9, next to the existing `BannedApiAnalyzers` upgrade note — which is also the real fix if the suite ever builds off Windows.

### Configuration error messages interpolate the offending value

`TestConfigurationException.ForKey(configurationKey, problem, offendingValue)` builds messages of the shape `Configuration key 'Site:BaseUrl' is invalid: expected an https URL. Value was: 'ftp://example.com'.` For every current caller that is exactly right — naming the bad value is what makes the message useful.

`Api:ApiKey` and `Api:TenantId` also pass through it, via `ReadRequiredText`. Traced through, no real secret can reach the message today: the only two throw paths fire when the value is `null` (printed as `(not set)`) or whitespace. The exposure is latent rather than live. Given that these exception messages land in build output, an allow-list of keys whose value is suppressed — or simply suppressing the value whenever the key name ends in `Key`, `Secret`, `Token` or `Password` — closes it before someone adds a length or format check on the key and leaks it.

### Scenario count: 18, not 17

`plan.md` item 10 and `context.json` both state 17 scenarios. The runner reports 18 — 9 API, 8 UI, 1 E2E, 0 failed, 0 skipped, confirmed here. `PageListing.feature` is three plain scenarios plus two outlines of two rows each, which is seven test cases from five scenario definitions; the planned set was built exactly as specified and 17 was arithmetic. FEAT-002 and FEAT-004 both recorded this, and README §5 and §6 state 18, which is the right call — a README that disagrees with the runner is worse than none. No action beyond noting that the task artefacts still carry the old number.
