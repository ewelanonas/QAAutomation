### Title comparison is the one place the two suites diverge

The E2E suite keeps the wait and the assertion on the same footing:

```csharp
this.waits.WaitUntilTitleContains(this.crossLayerContext.ApiTitle);
...
this.crossLayerContext.BrowserTitle.Should().ContainEquivalentOf(this.crossLayerContext.ApiTitle, ...);
```

`WaitUntilTitleContains` compares with `StringComparison.OrdinalIgnoreCase` and `ContainEquivalentOf` is the case-insensitive containment assertion, so the two cannot disagree. The UI navigation step uses the same wait and then the case-sensitive form:

```csharp
this.waits.WaitUntilTitleContains(expectedTitlePart);
...
this.siteNavigationContext.PageTitle.Should().Contain(expectedTitlePart, ...);
```

One window reaches it: the site changes "About Us" to "About us" in the landed page's title. The wait returns, the assertion fails, and the message is about casing rather than about navigation. Small window, readable failure — but it is the only place in the repository where two lines meant to agree about the same string do not.

### The entity gap in the cross-layer title rule

`RenderedText` documents the thing that makes this concrete rather than theoretical:

> The "rendered" name means "after the content filters have run", which is why a shortcode or an HTML entity can appear in it.

The configured slug, `technical`, has a plain title. The site's home page title is "Farm & Rural Estate Management Software | Landmark Systems", and this template's own verification record notes that the raw HTML carries `&amp;` where the DOM title carries a literal `&`. So a reader who repoints `Site:KnownPageSlug` at a page with an ampersand in its title gets a twenty-second `WaitUntilTitleContains` timeout with nothing to indicate that an entity caused it.

The step already carries a long comment explaining why containment rather than equality is the real contract. One more sentence there, naming which pages are usable, matches how the rest of the template handles this class of surprise — the AOS opacity trap and the newsletter timer are both written out in the files that have to live with them.

### Artefact folder creation is the one unguarded line in the capture path

`Capture` resolves and creates the scenario folder before the guarded writes begin:

```csharp
string folder = ArtefactPaths.ForScenario(this.artefactOptions.Directory, suiteName, scenarioTitle);
```

`ArtefactPaths.ForScenario` ends in `Directory.CreateDirectory`, and `Artefacts:Directory` is overridable through `QAAUTOMATION_Artefacts__Directory`. A path the operating system refuses throws out of `Capture`, out of the hook's `try`, and is reported as an `AfterScenario` failure beside the scenario's own — the same shape as the second pass's finding about one failing write suppressing the rest, one line earlier. The driver still quits, because that sits in the `finally`, so nothing leaks.
