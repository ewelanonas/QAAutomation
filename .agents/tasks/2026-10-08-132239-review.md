## High-level view

The three hard rules hold, and they hold structurally rather than by convention. No live content count is asserted anywhere: `PageListingSteps` reads `X-WP-Total` and `X-WP-TotalPages` through `PositiveIntegerParser` and asserts present-and-positive with the reason written out at length, the page-size step asserts `BeLessThanOrEqualTo` rather than equality, and the one `Should().Be(1)` in the API suite is slug uniqueness with a comment saying so. Nothing touches the hero carousel, the animated counters or an `h1` on the home page, and `HomePage` deliberately exposes no heading reader so a future author cannot. `ContactUsPage` has no submit method, and the prohibition plus its reasons are written at the top of both that class and `EnquiryForm.feature`.

Steering compliance is high and mechanically checkable. Repository-wide scans return no `using System.Linq`, no LINQ operator, no `var`, no `Thread.Sleep`, no `.Result`/`.Wait()`/`GetAwaiter`/`async void`, no `FluentAssertions`, none of the three banned Selenium packages, and no `Version` attribute on any `PackageReference`. All 16 packages are pinned in one `Directory.Packages.props`. `Core` carries no `ProjectReference`, `Tests.E2E` is the only project referencing both layers, no test project references another, and `Tests.Api` registers no driver and has no hooks class. `ElementWaits` is the only file holding a `WebDriverWait` or an `Until` lambda, and implicit wait is pinned at zero.

The four remaining findings are diagnosability and recorded-decision gaps rather than correctness faults, and three of them sit in the code that only runs once something has already gone wrong — the artefact capture and the API error path. That is the code a new QA meets on their first red build, so it is the worst place for the weakest lines.

The README answers the day-one question. Twelve sections, every PowerShell block defensive enough to paste safely, the `FullyQualifiedName` trap called out with all six generated fixture names, two Gherkin-to-code traces, and an honest-limitations section covering the production/read-only constraint, the no-content-count rule with its reasoning, the newsletter popup and the absent CI pipeline.

On security: credentials are `YOUR_API_KEY_HERE`/`YOUR_TENANT_ID_HERE` placeholders, configuration refuses any non-HTTPS base URL, nothing logs an `Authorization` header or a cookie, and the E2E hand-off host-checks a URL that came back in a response before navigating to it. No real key, token or connection string appears in any file.

### `ContainerStartup` is the one deviation nobody wrote down

`step-definitions.md`'s DI section opens with an unqualified ban: "Use the Microsoft DI container via `Reqnroll.Microsoft.Extensions.DependencyInjection`. Never `BoDi`, never service location, never static state." All three test projects then carry a `ContainerStartup.cs` that does two of those three things:

```csharp
using Reqnroll.BoDi;
...
[ModuleInitializer]
internal static void AllowTimeForTheFirstResolution()
{
    ObjectContainer.DefaultConcurrentObjectResolutionTimeout = FirstResolutionTimeout;
}
```

The code is right and the reason is good: FEAT-002 recorded a real cold-start failure where the second feature file gave up after one second waiting on the first `[ScenarioDependencies]` call and reported it as a potential circular dependency. The file explains the problem clearly, explains why a `[BeforeTestRun]` hook runs too late, and says the duplication across three projects is deliberate under the DAMP rule.

What it does not do is address the rule it crosses. Every other deliberate deviation in this template was pushed back into binding steering — `tech-stack.md` gained three package rows and the `AddRefitGeneratedClient` note, `bdd-gherkin-standards.md` gained `@marketing` and then the split-table exception, `step-definitions.md` gained the test-project-root placement, `ui-automation-selenium.md` gained the masking and driver-log deferrals, `project-structure.md` gained the `TestData/` deferral. This one was left as a comment in a source file, so the next reader who takes the DI section literally has grounds to delete it and will reintroduce an intermittent cold-start failure that only shows up on the first run after a build.

The fix is a sentence in that steering section saying the ban governs registration and resolution, and that raising `ObjectContainer.DefaultConcurrentObjectResolutionTimeout` from a `[ModuleInitializer]` is the one sanctioned exception because the runner exposes no other way to change it.

### A non-JSON refusal becomes a `JsonException` inside the client

`PagesClient.ReadError` is careful about the two cases it anticipated — `Error` is null on success, and a transport failure is an `ApiExceptionBase` that is not an `ApiException` and carries no body — then deserialises unconditionally:

```csharp
if (string.IsNullOrWhiteSpace(apiException.Content))
{
    return null;
}

return JsonSerializer.Deserialize<WordPressErrorResponse>(apiException.Content);
```

The third case is a refusal that carries a body which is not JSON. The target runs behind W3 Total Cache and Redis, so a 502 or 503 from the cache or edge layer arrives as an HTML error page with a non-empty body, and `JsonSerializer.Deserialize` throws `JsonException`.

That matters for diagnosis rather than correctness. `ReadError` is called before the wrapper record is returned, so the throw happens inside the client and the step never reaches its `StatusCode.Should().Be(...)` line. A QA reading the output sees a JSON parsing error and no status code at all, when the actual story — "the site answered 503" — was in hand. Guarding the deserialise and returning null, or checking `apiException.ContentHeaders` for `application/json` first, puts the status-code assertion back in charge of the failure message.

### One failing artefact write takes the other three with it

`FailureArtefacts.Capture` is the whole diagnostic story for this suite, since Selenium has no trace viewer. It runs its four writes in a bare sequence:

```csharp
SaveScreenshot(driver, folder);
SavePageSource(driver, folder);
SaveConsoleLog(driver, folder);
SaveLocation(driver, folder);
```

Only `SaveConsoleLog` has a guard, and it guards the log read rather than the capture as a whole. If `GetScreenshot()` throws — a browser that has already crashed, a disk with no space — the page source, the console log and `location.txt` are never written, and the folder is left holding nothing. The `try`/`finally` in `WebDriverHooks` catches this correctly from the driver's point of view (the browser still quits, so no process leaks) but it does not recover any of the three artefacts that would still have been readable.

The asymmetry is worth naming: the artefact most likely to fail is the screenshot, and the artefact most likely to explain a crash is `location.txt`, which is the last one attempted. Guarding each write individually, and noting the failure in the folder, costs four small blocks and makes a partial capture better than none.

### `Open()` uses a question as a wait

`HomePage.Open()` reads:

```csharp
this.driver.Navigate().GoToUrl(this.siteOptions.BaseUrl);
this.navigation.IsVisible();
```

`IsVisible()` returns a `bool` that is discarded. The wait is real — the method calls `ElementWaits.WaitUntilFirstVisible` internally and blocks until the nav appears — but nothing on the line says so, and C# raises no warning for an ignored return value.

For this audience that is a trap. A QA new to the language sees a call whose result goes nowhere, concludes it does nothing, and deletes it; the next run races the page load and the home page scenarios start failing one time in twenty. A `WaitUntilVisible()` method on `PrimaryNavigationComponent`, wrapping the same `ElementWaits` call and returning void, says what the line is for. `ContactUsPage.Open()` already gets this right — `this.waits.WaitUntilVisible(firstFieldLocator)` reads as the wait it is.
